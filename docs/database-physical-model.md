# 4.5.1 Global Physical Conventions

Status: APPROVED

## Decisions

### Primary keys and identifier generation

Approved hybrid primary-key strategy:

- Every table uses a technical primary key that is independent from business identifiers.
- `rag` domain entities use `UUID` when globally unique, externally transferable identifiers are beneficial.
- `rag` internal/high-volume structures such as `rag.chunks` may use `BIGINT` identity keys.
- `ops` uses `BIGINT` identity primary keys for operational structures, including runs, emails, attachments, service requests, establishments, and execution logs.
- `audit.security_events` uses a `BIGINT` identity primary key because it is chronological and log-oriented.
- Business identifiers such as `protocol_number` and `establishment_number` remain separate from database primary keys.
- PostgreSQL generates primary-key identifiers whenever possible.
- `UUID` primary keys use `DEFAULT gen_random_uuid()`.
- `BIGINT` primary keys use `GENERATED BY DEFAULT AS IDENTITY`.
- Application components must not manually coordinate, increment, or synthesize database primary-key values.

### PK and FK naming

- Primary-key columns use entity-specific names rather than generic `id`.
- Examples include `source_id`, `document_id`, `chunk_id`, `run_id`, `email_id`, `request_id`, and `event_id`.
- A foreign-key column reuses the exact name of the referenced primary-key column whenever the relationship represents that entity directly.
- Example: `rag.documents.source_id` references `rag.sources.source_id`.

### Constraint naming

Use explicit deterministic names:

- primary key: `pk_<table>`
- foreign key: `fk_<table>__<column>`
- unique constraint: `uq_<table>__<column_or_columns>`
- check constraint: `ck_<table>__<rule>`

Examples:

- `pk_documents`
- `fk_documents__source_id`
- `uq_service_requests__protocol_number`
- `ck_email_attachments__establishment_count_nonnegative`

### Index naming

- Standard indexes use `idx_<table>__<column_or_columns>`.
- Specialized indexes may expose the index technology in the name when useful for operations and investigation.
- PostgreSQL Full Text Search GIN indexes use a `gin_` prefix, for example `gin_chunks__search_vector`.
- pgvector HNSW indexes use an `hnsw_` prefix when HNSW is approved, for example `hnsw_chunks__embedding`.
- An index must have a concrete query or operational use case; indexes are not created merely because a column exists.

### Timestamp strategy

- Every field that represents an instant in time uses PostgreSQL `TIMESTAMPTZ`.
- `TIMESTAMP WITHOUT TIME ZONE` is not used for event instants in the approved model.
- PostgreSQL and application runtime operate internally in UTC.
- Conversion to a user's or business-local timezone occurs only at presentation/integration boundaries that require it.
- Timestamp columns use names ending in `_at`, including `created_at`, `updated_at`, `started_at`, `finished_at`, `received_at`, `processed_at`, `occurred_at`, `upload_at`, `download_at`, `completed_at`, `return_email_at`, and `reviewed_at`.
- PostgreSQL native timestamp precision is preserved; timestamps are not artificially truncated to seconds or milliseconds.

### Temporal audit fields

- `created_at` is `NOT NULL DEFAULT now()` on entities that conceptually include the field.
- `updated_at` exists only on mutable entities where the conceptual model already requires it.
- `updated_at` is maintained explicitly by the application; no global hidden trigger is introduced.
- Historical/event records do not receive `updated_at` automatically.
- Domain timestamps such as `started_at`, `finished_at`, `occurred_at`, `received_at`, `upload_at`, and `download_at` represent the domain event itself.
- `created_at` represents persistence/record creation time and does not replace domain-event timestamps.

### Boolean strategy

- Boolean values use PostgreSQL `BOOLEAN`.
- Do not represent booleans as `0/1`, `S/N`, `Y/N`, or textual substitutes.
- Boolean column names should express a condition when such fields are introduced, for example `is_active` or `has_error`.
- Multi-state lifecycle concepts must remain status fields rather than being collapsed into booleans.
- A boolean default is defined only when the initial state is unambiguous; otherwise the application must provide the value explicitly.

### Text types

- `TEXT` is the default PostgreSQL type for textual data.
- `VARCHAR(n)` is used only when the length limit is a real domain rule or an externally imposed integration constraint.
- Arbitrary limits such as `VARCHAR(255)` are not introduced without a documented requirement.
- Field-specific limits, where justified, are defined later in the table-level physical specifications.

### Nullability, statuses, and conceptual enums

- Use `NOT NULL` when a value must exist when the record is created.
- Use `NULL` when absence represents a legitimate lifecycle state such as "not yet happened" or "not applicable".
- Lifecycle timestamps such as `finished_at`, `processed_at`, `completed_at`, `upload_at`, `download_at`, `return_email_at`, and `reviewed_at` may therefore be nullable when their event has not yet occurred.
- Status and small categorical fields use `TEXT + CHECK` during the POC.
- PostgreSQL `ENUM` is not the default status representation for this POC.
- Separate domain/lookup tables are not introduced solely to represent small static status sets.
- Status values and their exact `CHECK` sets are defined per table during the detailed physical-model subsections.

### Naming conventions

- Schemas, tables, columns, constraints, and indexes use lowercase `snake_case`.
- Identifiers should be descriptive and stable rather than abbreviated without clear need.
- Physical names should remain consistent across `rag`, `ops`, and `audit`.

### Foreign-key behavior

- Mandatory relationships use `NOT NULL` foreign keys.
- Optional relationships use nullable foreign keys.
- There is no global `ON DELETE CASCADE` policy.
- The default deletion behavior is restrictive (`NO ACTION` / `RESTRICT`) to protect integrity and historical traceability.
- `ON DELETE CASCADE` is used only for true composition relationships where the child has no independent meaning, and only after explicit table-level approval; document-to-current-chunks is a candidate example.
- `ON DELETE SET NULL` may be used for historical/log relationships that must survive deletion of the referenced parent, when the table-level design justifies it.
- Primary keys are treated as immutable; `ON UPDATE` therefore remains restrictive/default rather than cascading key changes.

### Defaults

- Database-generated technical defaults are preferred for deterministic infrastructure values such as primary keys and `created_at`.
- Counters and boolean fields may receive database defaults only when a single valid initial state is explicitly established.
- Business-state defaults are created only when the domain has one unambiguous initial state.
- When no unambiguous default exists, the application must provide the value explicitly.
- Defaults must not conceal missing business information or convert an unknown state into an assumed value.

### RAG publication lifecycle

For the same stable document identity, a checksum equal to the successfully
published checksum is skipped only when the document is usable and no rebuild
is requested. The skip records `SKIPPED_UNCHANGED`, `SKIPPED`, and zero created
chunks without changing current chunks.

For changed content or an explicit rebuild, chunking, embedding, and FTS
preparation occur outside the publication transaction. A single ingestion
worker serializes publication per document. The transaction deletes current
chunks, inserts the complete replacement set, updates the document checksum
and `last_ingested_at`, persists the successful run and committed chunk count,
and commits as one unit.

If publication fails or produces zero usable chunks, the transaction rolls back;
the previously valid active chunks remain available. The error run is persisted
separately after rollback. If the connection outcome at commit is unknown, the
application reconnects and inspects the persisted run outcome before retrying.

An inactive document is not automatically reactivated by successful
reingestion. Retrieval requires both the source and document to be `ACTIVE`.
No document or chunk history is introduced.

Run lifecycle invariants are:

- `RUNNING` requires `finished_at IS NULL` and `chunks_created = 0`.
- Terminal statuses require `finished_at IS NOT NULL` and
  `finished_at >= started_at`.
- `ERROR` and `SKIPPED` require zero committed chunks.
- `SUCCESS` requires a positive committed chunk count.

Document deletion preserves ingestion history, nulling only the optional
`document_id` while retaining mandatory `source_id`. The source/document
agreement is enforced by the composite foreign key.

Hybrid lexical, semantic, and provenance retrieval for one request must observe
a consistent chunk set through one SQL statement or a read-only
`REPEATABLE READ` transaction.

# 4.5.3 Final FastEmbed Model

Status: APPROVED

## Selected model

`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`

FastEmbed `0.8.0` is the current project pin. This multilingual model is
suitable for the POC, including Portuguese content.

## Embedding dimension

`384`

## Runtime

FastEmbed uses ONNX Runtime on local CPU. GPU acceleration is optional and is
never required. The embedding layer uses no external embedding API or
credential and remains independent from the LLM provider.

## Pooling and normalization

The approved current behavior is FastEmbed mean pooling for this model. No
additional manual embedding normalization is applied. This does not change
the approved pgvector distance metric documented in phase 4.5.5.

## VECTOR(384)

The approved `rag.chunks.embedding` representation is `VECTOR(384) NOT NULL`.

## Local CPU validation

The cached-run validation passed on the project development machine: model load
was approximately 1.24 seconds and 100 chunks were embedded in approximately
1.09 seconds, or 10.87 milliseconds per chunk (92.03 chunks per second).
Output dimension was confirmed as 384. The initial download/load time is not a
steady-state latency measurement. Local CPU execution is suitable for the POC.

## Compatibility and re-embedding

`intfloat/multilingual-e5-small` is superseded as the active FastEmbed model.
Embeddings from E5, prior sentence-transformers runtime configurations, or any
incompatible configuration must not be mixed with this representation. A full
re-embedding is required when model, dimension, pooling behavior,
normalization policy, or semantic input processing changes. Vectors are never
converted between dimensions.

FTS configuration remains in phase 4.5.4. Vector distance, initial exact
search, and the future-only HNSW boundary are approved in phase 4.5.5;
executable semantic retrieval remains an implementation concern.

## 4.5.3 completion

The final FastEmbed model is approved. FTS and pgvector are specified in
4.5.4 and 4.5.5; final phase status is recorded in 4.5.16. No schema, table,
DDL, migration, ORM model, or database object is created by this decision.

# 4.5.4 PostgreSQL Full Text Search

Status: APPROVED

## Search-vector column

`rag.chunks.search_vector` is `TSVECTOR NOT NULL` and is separate from
`rag.chunks.embedding VECTOR(384)`. It is mandatory for every published chunk;
an empty `TSVECTOR` is valid when the configured parser produces no lexemes.

## Text-search configurations

The POC uses two standard PostgreSQL configurations:

- `portuguese` for stemming, morphology, and business-rule language.
- `simple` for exact technical identifiers and terms such as `FastAPI`,
  `pgvector`, `protocol_number`, `R1`, `R2`, `EC`, acronyms, and field names.

No custom tokenizer, parser, thesaurus, or synonym configuration is introduced.
The final FTS configuration remains limited to standard PostgreSQL behavior.

## Inputs and weights

The application controls generation using PostgreSQL native
`to_tsvector(...)`; Python stemming, database triggers, and generated columns
are not used. The allowed source fields are `rag.documents.title`,
`rag.chunks.section`, and `rag.chunks.content`. Keys, foreign keys, checksums,
statuses, timestamps, embeddings, metadata JSONB, and operational fields are
excluded by default.

The approved PostgreSQL weight hierarchy is:

- `A`: document title;
- `B`: chunk section;
- `C`: chunk content processed with `portuguese`;
- `D`: technical/exact text processed with `simple`.

The technical/exact input is derived from the allowed title, section, and
content fields; no additional first-class technical-text column is introduced.
The application stores the complete positional result before publication.

When a document title, chunk section, or chunk content changes, affected
`search_vector` values are regenerated. A document-title change rebuilds the
FTS representation for its affected chunks.

## Publication lifecycle

FTS preparation occurs before atomic publication in the sequence
`load -> validate -> chunk -> embed -> FTS -> publish`. No partial chunk set is
published. The FTS representation is committed with the current chunks and
the corresponding document publication outcome.

## Planned GIN index

The planned index name is `gin_chunks__search_vector` on
`rag.chunks.search_vector`. It is PLANNED ONLY in phase 4.5.4; no DDL,
migration, index creation, or database object is created by this document.

## Lexical query and ranking

The application parses user input with native
`websearch_to_tsquery('portuguese', user_query)` combined with
`websearch_to_tsquery('simple', user_query)`. Raw `to_tsquery()` is forbidden
for user queries. Lexical ranking uses `ts_rank_cd` to retain positional
information and term proximity; positions are not stripped from
`search_vector`.

Lexical candidates are eligible only when both
`rag.sources.status = 'ACTIVE'` and `rag.documents.status = 'ACTIVE'`.
The lexical candidate limit is at most 10. The semantic candidate limit remains
at most 10, hybrid fusion remains Reciprocal Rank Fusion (RRF), and final
response context remains Top-K 5 with no ML reranker.

## 4.5.4 completion

The PostgreSQL FTS physical model is approved. The approved pgvector and OPS
models follow below; final phase status is recorded in 4.5.16.

# 4.5.5 pgvector Physical Model

Status: APPROVED

## Vector representation

`rag.chunks.embedding` is `VECTOR(384) NOT NULL`, matching the approved
FastEmbed 0.8.0 / `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`
configuration from 4.5.3. The embedding representation is not changed here.

## Similarity metric

The initial semantic metric is cosine distance using the pgvector `<=>`
operator. Conceptual ordering is `embedding <=> :query_embedding ASC`:
lower distance means higher similarity. Only the raw distance is retained;
no percentage or normalized user-facing score is defined. Inner product and
L2 distance are prohibited for the initial model, with no dynamic metric
selection.

## Initial search and future ANN boundary

The initial search strategy is an exact nearest-neighbor scan with no vector
ANN index. This preserves full recall at the POC volume and avoids premature
tuning. If benchmarks later require ANN, HNSW is evaluated before IVFFlat;
neither is active now and no DDL or migration is created. The reference HNSW
baseline is `vector_cosine_ops`, `m=16`, `ef_construction=64`, and
`ef_search=40`; these values are documentation-only and are not validated or
implemented.

## Conceptual semantic retrieval contract

Semantic retrieval conceptually joins `rag.chunks` to `rag.documents` and
`rag.sources`, filters `s.status = 'ACTIVE'` and `d.status = 'ACTIVE'`, orders
by `c.embedding <=> :query_embedding ASC`, and limits semantic candidates to
10. This is a documentation contract, not an executable query or runtime
implementation.

Hybrid retrieval consumes lexical and semantic rank positions 1 through 10
with Reciprocal Rank Fusion (RRF). Raw lexical and vector scores are never
combined or normalized across channels, and no ML reranker is introduced.
Lexical, semantic, and provenance retrieval for one request must observe the
same committed chunk set through one SQL/CTE statement or a read-only
`REPEATABLE READ` transaction.

## 4.5.5 completion

The pgvector physical model is approved: `VECTOR(384)`, cosine distance via
`<=>`, exact search with no active ANN index, active source/document filters,
semantic Top 10, rank-based RRF, and snapshot consistency. Final phase status
is recorded in 4.5.16. No
database object, DDL, migration, vector index, or semantic runtime query is
created by this decision.

## OPS lifecycle and boundaries

`ops.automation_runs` records R1/R2 execution status. R1 has a 1:N
relationship to `incoming_emails`; each email has 1:N `email_attachments` and
0..1 `service_requests`. A service request owns N establishments and reuses
one protocol across repeated R2 runs. R2 reads the request protocol and
`generated_file_name`, then updates establishment current state without
erasing R1 history.

`ops.execution_log` is the immutable chronological operational history for
normal R1/R2 execution, failures, and timeouts. It is not
`audit.security_events`: security and governance events remain owned by AUDIT.
All result messages and log messages contain sanitized operational information
only.

# 4.5.11 Delete, Retention, and Cascade Behavior

Status: APPROVED

| Domain relationship | Delete action | Retention/lifecycle policy |
|---|---|---|
| `rag.sources -> rag.documents` | `ON DELETE RESTRICT` | Normal withdrawal uses `status = 'INACTIVE'`; no routine physical delete |
| `rag.documents -> rag.chunks` | `ON DELETE CASCADE` | Sole approved cascade; chunks are true composition children |
| `rag.documents -> rag.ingestion_runs` | `ON DELETE SET NULL (document_id)` | Preserve run history and mandatory `source_id` |

| OPS operational parents -> children | `ON DELETE RESTRICT` | Applies to runs/emails, emails/attachments, emails/requests, requests/establishments, and attachments/establishments; use lifecycle status instead of routine deletion |

| All technical PK references | `ON UPDATE RESTRICT` | Technical keys are immutable |

There is no blanket cascade policy and no arbitrary 30-, 90-, or 365-day
AUDIT retention. Physical removal requires an explicit authorized workflow
defined outside this phase. The deletion model does not move operational logs
into AUDIT and does not reproduce legacy Oracle retention behavior.

# 4.5.13 Physical Model Security

Status: APPROVED

## Global field review

Every field in all 11 tables is subject to the same anti-secret rule.
No field intentionally stores passwords, API keys, access/refresh/session
tokens, cookies, private keys, DB credentials, credential-bearing connection
strings, .env values, secret locations, protected secret paths, raw
credential-bearing dumps, or authentication-bypass material. Category labels
such as API_KEY describe a class of resource; they never authorize its value.

This includes all free text and JSONB: result_message, message, result,
failure_reason, validation_message, rejection_reason, review_note,
sanitized_content, subject, section, references, filenames, and metadata.
Sanitization is an application/governance responsibility before persistence,
not a guarantee supplied by a nonblank CHECK.

| Reviewed table | Physical security and minimization boundary |
|---|---|
| rag.sources | Governed identity, classification and reference; no protected credential information or secret location |
| rag.documents | Governed descriptive fields and checksum; no private operational dump or authentication material |
| rag.chunks | Approved knowledge and complementary metadata only; no uncontrolled Web Search payload, generated LLM answer promoted to knowledge, or unrestricted infrastructure detail |
| rag.ingestion_runs | Sanitized operational outcomes and governed provenance |
| ops.automation_runs | Operational run facts and sanitized result_message |
| ops.incoming_emails | Necessary sender/recipient/subject and validation facts; sanitized rejection_reason; no body or CC list |
| ops.email_attachments | Filename only, never protected full path; sanitized validation_message |
| ops.service_requests | Necessary protocol state; sanitized result/failure_reason and no credential-bearing operational dump |
| ops.establishments | Necessary EC/file state; generated_file_name is a filename only; sanitized result_message |
| ops.execution_log | Sanitized chronological operational message, never raw dumps or credential/Oracle infrastructure secrets |
| audit.security_events | Sanitized evidence and review_note; opaque authorized user/request correlation; no raw request, full prompt, secret payload, or debug dump |

OPS does not gain attachment paths, Windows directories, environment
credentials, secret-storage paths, or infrastructure-specific secret metadata.
RAG source governance remains mandatory and independent of retrieval ranking.

guaranteed, sanitized_content is NULL. No secret-detection trigger, procedure,

introduce review tables or a workflow implementation.

## IAM scope

Production authorization is outside phase 4.5. No production DB users,
application roles, GRANT/REVOKE matrix, RLS, Vault integration, credential
rotation, or production secret-management architecture is introduced.
The development read-only PostgreSQL MCP remains external tooling and is not
a runtime dependency. This review approves the field policy; implementation
and enforcement tests remain future work.

## Time, statuses, nullability, and deletion

All instants use TIMESTAMPTZ with UTC internally and native PostgreSQL
precision. Presentation timezone conversion occurs only at boundaries.
created_at is persistence time; domain timestamps represent actual domain
events. updated_at is application-maintained without a global update trigger.
Lifecycle timestamps remain nullable until the event occurs.

NULL means not yet occurred, not yet known, not applicable, or an unresolved
optional relationship. It is not a generic error, empty string, or arbitrary
missing data. Active runs have finished_at NULL; unprocessed emails have
processed_at NULL; an unknown establishment count is NULL while known zero is
0; incomplete requests have completed_at NULL; uploads not yet done have
upload_at NULL; unreviewed security events have reviewed_at NULL; failure
before document resolution may leave ingestion_runs.document_id NULL.
The complete mandatory/nullable column matrix remains in 4.5.10.

The 4.5.11 delete matrix remains authoritative: restrictive ownership, sole
CASCADE from rag.documents to rag.chunks, targeted SET NULL of ingestion
document_id retaining source_id, and SET NULL for optional execution-log
entity references. The mandatory log run anchor remains RESTRICT.
Normal withdrawal uses lifecycle status, not routine physical deletion.
AUDIT has no parent FK, automatic TTL, or arbitrary purge period.
