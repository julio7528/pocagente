Visão geral da POC

Como o Getnet Support foi construído

Conheça o desafio, a arquitetura e os recursos que organizam cada resposta.

O desafio

Multiagentes com papéis claros

  • Três ou mais agentes especializados
  • Roteamento e coordenação de tarefas
  • API HTTP em JSON e execução em Docker

O problema

Cada pedido pede evidências diferentes

  • Conhecimento interno e informações Getnet
  • Dados operacionais com acesso controlado
  • Busca pública ou apoio humano quando necessário

O objetivo da POC

Atendimento fundamentado e coordenado

  • Agentes cooperam além de um chat genérico
  • Respostas relacionadas às fontes consultadas
  • Qualidade e operação podem ser avaliadas

Capacidades

Componentes integrados com limites claros

  • RAG híbrida, RRF e citações
  • Ferramentas OPS autorizadas e somente leitura
  • Busca web, segurança, auditoria e handoff

Como funciona o RAG

Da preparação dos documentos à busca híbrida, cada resposta parte de evidências recuperadas e organizadas para grounding.

Do conteúdo aprovado ao conhecimento consultável

ENGINEERING DECISIONS

Decisões Arquiteturais

Escolhas que definem fronteiras claras, controle de dados e respostas sustentadas por evidências.

DECISÃO 01

PostgreSQL nativo + Psycopg 3

Decisão

O Agent API acessa PostgreSQL com Psycopg 3 assíncrono e SQL parametrizado; ORM não é requisito para esse runtime.

Motivo

A solução depende de recursos PostgreSQL como pgvector, Full Text Search, JSONB e transações explícitas.

Resultado

O banco permanece uma plataforma única, enquanto migrations SQL nativas e o driver assíncrono mantêm o runtime próximo dos recursos usados.
